description: Fix exactly ONE JIRA bug ticket assigned to me in "BUG - Blocked by Defect", confirm via re-run, then stop
---

Follow the workflow defined in `.claude/tasks/zephyr-bug-fixes.md` in this repo, but fix **only a single bug ticket** on this invocation, then stop. Do not loop over multiple tickets.

Unlike `/zephyr-bug-fix-one` (which walks `BUG_TICKET_LOGS`, the record of tickets `zephyr-bug-tickets.md` itself created), this command goes straight to the JIRA board: any ticket in status **"BUG - Blocked by Defect"** assigned to me, regardless of how it got there — including ones created by hand, outside that task entirely.

Argument (optional, `$ARGUMENTS`): a JIRA bug ticket key (e.g. `EI-3470`) to target a specific ticket. If omitted, pick the first unprocessed one per step 2 below.

Steps:

1. Read `.claude/tasks/zephyr-bug-fixes.md` for the full spec (env vars, ticket parsing, code-location logic, close-out steps, log format) — specifically its "Picking which ticket to fix — via board status + assignee" section for this command.
2. Read `BUG_FIX_LOGS` (create it if it doesn't exist yet, path from the `BUG_FIX_LOGS` env var — add it to `.env` first if missing: `BUG_FIX_LOGS=<repo>\zephyr-automation\bug_fixes_log.txt`) and collect every JIRA key already logged there (any line's `JIRA:` field).
   - If `$ARGUMENTS` was given: `getJiraIssue` it directly and confirm `fields.status.name` is exactly `"BUG - Blocked by Defect"` and `fields.assignee.accountId` is you. If either isn't true, or the key is already in `BUG_FIX_LOGS`, report that and stop without doing anything — this command never claims a ticket, unlike `/zephyr-bug-fix-one`.
   - If no argument: `searchJiraIssuesUsingJql` with `project = EI AND status = "BUG - Blocked by Defect" AND assignee = currentUser() ORDER BY created ASC` (`cloudId: "softwaretestinghub.atlassian.net"`). Walk the results in order and pick the first key NOT yet in `BUG_FIX_LOGS`. If none remain, report that every ticket assigned to you in that column already has a logged fix attempt and stop.
3. `getJiraIssue` the target ticket (skip the re-fetch if step 2's `$ARGUMENTS` path already has it). Parse the summary for its category (`[BUG] [FrontEnd|BackEnd] <name>` — use as-is, don't re-derive) and the description for its `**Reason**` (STEPS/EXPECTED/ACTUAL), `**API**` line(s) if BackEnd, and `**Zephyr Test Cases**` list — that list is authoritative for which executions to check/re-run in steps 4 and 7. If the description doesn't have these sections at all (likely for a ticket created by hand rather than by `zephyr-bug-tickets.md`), don't guess a structure that isn't there — report it as unparseable per the spec's "If something doesn't fit" and stop without logging anything.
4. **Check whether it's already fixed, before touching any code — or re-running anything.** For each execution in step 3's `**Zephyr Test Cases**` list, `GET` its current Zephyr status/comment **first**. A developer may have already investigated and shipped a fix with the reasoning recorded directly on the execution — that record is more authoritative than a stale local test, so don't overwrite it with a generic one. If the `GET` shows Pass with genuine investigation content, treat that as the confirmed result directly (skip re-running the local test for it), go to step 8 for the PR citation (the Zephyr comment may already name it directly — use that instead of a fresh `git log` search when it does), and note in the final summary if that comment names a related ticket sharing the same root cause so it isn't rediscovered later.
   - Only for executions where the Zephyr `GET` doesn't already show a confirmed, reasoned result: re-run the matching automated test for real against the live QA host right now — its `BUG_FIX_LOGS`/ticket history is not proof it's still broken; the underlying code may have moved since.
   - If **every** execution is already resolved (via the Zephyr check or the live re-run): skip step 5 (locate/fix) and step 6's drift-check/commit/deploy concerns entirely — none of it applies. Go straight to step 7's `PUT`/log using the confirmed result (the execution's own Zephyr status may still need updating even for a live-re-run pass).
   - If **some** still fail: do step 5 only for those. The already-resolved one(s) don't need to be re-run again in step 7 — carry that result forward.
   - If **all** still fail: continue to step 5 exactly as before.
5. Locate and fix the defect (only for executions still failing per step 4) per the spec's "Locating and fixing the code" section:
   - **BackEnd** (`eruditiontx-services-mvp`): trace the `**API**` line's `METHOD path` to its route handler; also find and run the matching test in `teacher-student-automation/service/tests/` once, unmodified, against `https://eruditionsolutionsqa.com` to reproduce the failure first.
   - **FrontEnd** (`eruditiontx-client-mvp`): find and run the matching test in `teacher-student-automation/client/tests/` first to reproduce, then trace into the relevant component/hook/page.
   - Read that subproject's own `CLAUDE.md` before editing. Make the minimal fix for the gap between EXPECTED and ACTUAL. **Leave it as an uncommitted working-tree change** — do not commit or push automatically; name the exact file(s) changed in the final summary.
6. **Before trusting any re-run, make sure the fix is actually live.** A local edit in `eruditiontx-services-mvp` does nothing to the live QA host on its own — check `git fetch` + `git rev-list HEAD..origin/DEVELOPMENT --count` for drift first, and know that the host only updates from a push to `DEVELOPMENT` (CI/CD does `git reset --hard` + restart on push). **Ask the user before committing/pushing** — this is a shared, auto-deploying branch, not a default action — and when they approve, commit **without** a `Co-Authored-By: Claude ...` line (standing instruction for this project, not optional). After pushing, poll the live host (re-run the test every ~20s; a few minutes is normal) until the deploy lands before treating any result as real.
7. For **every** execution in step 3's `**Zephyr Test Cases**` list: re-run its automated test for real against the live QA host — unless it already passed in step 4 and nothing since could have changed that, in which case reuse that result. Then `PUT https://prod-api.zephyr4jiracloud.com/v2/testexecutions/<Execution.Key>` with `{"statusName": "Pass"|"Fail", "comment": "<STEPS/EXPECTED/ACTUAL HTML per zephyr-jira-sync.md's template, ACTUAL reflecting the real, current outcome>"}`. Re-`GET` to confirm `testExecutionStatus.id` actually changed (`14539939`=Pass, `14539940`=Fail) before trusting it — if it didn't, treat that one execution as unconfirmed/blocked rather than guessing a result.
8. **For any execution that was already passing in step 4 (no fix made this run), find the responsible PR/commit** per the spec's "Finding the responsible PR/commit" section — don't just write "already fixed" in the comment. Locate the relevant file(s) the same way step 5 would have; `git log --oneline -n 30 -- <file(s)>` (and `origin/DEVELOPMENT` too if the local checkout is behind — same drift check as step 6) for a commit dated after the ticket's `created` field whose subject plausibly matches this scenario, `git show` it to confirm the diff actually explains the behavior, then build a PR URL from its trailing `(#<N>)` and the real `github.com/Eruditiontx/<repo>` (not any SSH host alias `git fetch` output shows). Carry the commit hash, PR link, author, and a plain paraphrase into step 10's Solution. If a real search turns up nothing plausible, fall back to noting it was already passing with the cause untraced — don't fabricate a citation. Skip this step entirely if step 4 found every execution still failing.
9. If a still-failing execution turns out to conflict with a **deliberate, documented design decision** elsewhere in the codebase — that's a confirmed, honest `Fail`, not a process blocker. It still goes through steps 7–11 exactly like any other result: `PUT` the real `Fail` (step 7), comment explaining *why* it's failing and what design tension it surfaces (step 10 below), transition to In Progress, and log `FAILED`. Don't divert this into "step 11's ... don't log" fallback — that's for genuine process failures only (unparseable ticket, untraceable code, an erroring API call, a write that won't confirm), not for a legitimate reason not to change the code.
10. Once every execution's real result is confirmed (whether all passed or not):
    - **Comment** on the ticket covering **Issue** (root cause), **Solution** (what was changed this run; or, for an execution already fixed per step 4, the PR/commit found in step 8 — link, hash, author, paraphrase, not just "already passing"; or, per step 9, that it conflicts with a deliberate design decision — cite what that decision is and where it's documented; or, for an ordinary unresolved failure, what was tried and what's still broken), and **Remarks** (edge cases, follow-ups, which executions if any still fail).
    - **Transition** the ticket to **In Progress**: call `getTransitionsForJiraIssue` and match by **target status name** (`to.name`, case-insensitive `"in progress"`), not by the transition's own `name` field — this board has a transition literally labeled "In Progress" that actually targets a different status (`"TO DO (Exclude SKIPPED, INFRA)"`); the real one, confirmed on this board, targets status `"IN PROGRESS"`. Apply it, then `getJiraIssue` again and confirm `fields.status.name` is `"IN PROGRESS"` (case-insensitive); if not, flag it as unresolved in the summary but continue to the logging step regardless.
11. Append one line per execution from step 7 to `BUG_FIX_LOGS`: `JIRA:<Bug ticket key>, EXEC:<Execution.Key>, TESTCASE:<Test Case.Key>, RESULT:PASSED|FAILED` — only after step 10 has run, not before. If step 4/5/6 never reached a confirmable result at all (unparseable ticket, code location couldn't be traced, a Zephyr write never took, etc. — not the deliberate-design-decision case from step 9, which does get logged), don't log anything for this ticket — report the blocker per the spec's "If something doesn't fit" instead.
12. **No confirmation needed before checking/commenting/transitioning/logging** — that part proceeds straight through once the real result is known. Committing/pushing the code change is the one exception: always ask the user first (see step 6), whether that happens mid-task (BackEnd, to reach a real verification) or after — and it may not be needed at all, if step 4 found it already fixed. Report what was done (ticket key, category, already-fixed vs newly-fixed vs still-broken per execution, PR cited if any, file(s) changed if any, whether/what was committed, transition outcome) in the final summary.
13. Stop after this one ticket. Do not automatically continue to the next one — run `/zephyr-bug-fix-mine` again for the next item.
