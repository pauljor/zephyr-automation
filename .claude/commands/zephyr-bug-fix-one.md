---
description: Fix exactly ONE JIRA bug ticket's underlying defect, confirm via re-run, then stop
---

Follow the workflow defined in `.claude/tasks/zephyr-bug-fixes.md` in this repo, but fix **only a single bug ticket** on this invocation, then stop. Do not loop over multiple tickets.

Argument (optional, `$ARGUMENTS`): a JIRA bug ticket key (e.g. `EI-3455`) to target a specific ticket. If omitted, pick the first unprocessed ticket per step 3 below.

Steps:

1. Read `.claude/tasks/zephyr-bug-fixes.md` for the full spec (env vars, ticket parsing, code-location logic, close-out steps, log format).
2. Read `BUG_TICKET_LOGS`. Group its rows by the JIRA ticket key (3rd field, `JIRA:<key>`) — a `PREEXISTING` row points at the same ticket as an earlier row (consolidation), so build one map entry per distinct JIRA key listing every {Test Case.Key, Execution.Key} pair logged against it.
3. Read `BUG_FIX_LOGS` (create it if it doesn't exist yet, path from the `BUG_FIX_LOGS` env var — add it to `.env` first if missing: `BUG_FIX_LOGS=<repo>\zephyr-automation\bug_fixes_log.txt`) and collect every JIRA key already logged there (any line's `JIRA:` field).
   - If `$ARGUMENTS` was given: use that key directly. If it isn't in `BUG_TICKET_LOGS`, or it's already in `BUG_FIX_LOGS`, report that and stop without doing anything.
   - If no argument: pick the first JIRA key (in `BUG_TICKET_LOGS` order) from step 2 that is NOT yet in `BUG_FIX_LOGS`. If none remain, report that every ticket already has a logged fix attempt and stop.
4. `getJiraIssue` the target ticket. Parse the summary for its category (`[BUG] [FrontEnd|BackEnd] <name>` — use as-is, don't re-derive) and the description for its `**Reason**` (STEPS/EXPECTED/ACTUAL), `**API**` line(s) if BackEnd, and `**Zephyr Test Cases**` list — that list is authoritative for which executions to check/re-run in steps 6 and 9, taking priority over what step 2 found if the ticket was consolidated more recently. `fields.assignee` comes back by default — no need to request it explicitly.
5. **Claim the ticket** if it's unassigned: if `fields.assignee` is `null`, get your own `accountId` via `atlassianUserInfo` (cache it rather than re-fetching per ticket), then `editJiraIssue` with `fields: {"assignee": {"accountId": "<your accountId>"}}`, and `getJiraIssue` again to confirm `fields.assignee.accountId` matches. If it's already assigned to someone else, leave it — don't reassign — and note the existing assignee in the final summary.
6. **Check whether it's already fixed, before touching any code.** For every execution in step 4's `**Zephyr Test Cases**` list, re-run its automated test for real against the live QA host **right now**. Confirmed happening on `EI-3456` (2026-09-25): its "excessively long class code" scenario was already fixed live as a side effect of `EI-3455`'s deploy, for a completely different ticket — `BUG_TICKET_LOGS`/the ticket's own `FAILED` history is not proof it's still broken.
   - If **every** execution already passes: skip step 7 (locate/fix) and step 8's drift-check/commit/deploy concerns entirely — none of it applies. Go straight to step 9's `PUT`/log using this confirmed result (the execution's own Zephyr status may still need updating even though the live test already passes).
   - If **some** still fail: do step 7 only for those. The already-passing one(s) don't need to be re-run again in step 9 — carry this result forward.
   - If **all** still fail: continue to step 7 exactly as before.
7. Locate and fix the defect (only for executions still failing per step 6) per the spec's "Locating and fixing the code" section:
   - **BackEnd** (`eruditiontx-services-mvp`): trace the `**API**` line's `METHOD path` to its route handler; also find and run the matching test in `teacher-student-automation/service/tests/` once, unmodified, against `https://eruditionsolutionsqa.com` to reproduce the failure first.
   - **FrontEnd** (`eruditiontx-client-mvp`): find and run the matching test in `teacher-student-automation/client/tests/` first to reproduce, then trace into the relevant component/hook/page.
   - Read that subproject's own `CLAUDE.md` before editing. Make the minimal fix for the gap between EXPECTED and ACTUAL. **Leave it as an uncommitted working-tree change** — do not commit or push automatically; name the exact file(s) changed in the final summary.
8. **Before trusting any re-run, make sure the fix is actually live.** A local edit in `eruditiontx-services-mvp` does nothing to the live QA host on its own — check `git fetch` + `git rev-list HEAD..origin/DEVELOPMENT --count` for drift first (confirmed 135 commits on `EI-3455`; fast-forward if it's a clean behind-only gap), and know that the host only updates from a push to `DEVELOPMENT` (CI/CD does `git reset --hard` + restart on push). **Ask the user before committing/pushing** — this is a shared, auto-deploying branch, not a default action — and when they approve, commit **without** a `Co-Authored-By: Claude ...` line (standing instruction for this project, not optional). After pushing, poll the live host (re-run the test every ~20s; a few minutes is normal) until the deploy lands before treating any result as real.
9. For **every** execution in step 4's `**Zephyr Test Cases**` list: re-run its automated test for real against the live QA host — unless it already passed in step 6 and nothing since could have changed that, in which case reuse that result. Then `PUT https://prod-api.zephyr4jiracloud.com/v2/testexecutions/<Execution.Key>` with `{"statusName": "Pass"|"Fail", "comment": "<STEPS/EXPECTED/ACTUAL HTML per zephyr-jira-sync.md's template, ACTUAL reflecting the real, current outcome>"}`. Re-`GET` to confirm `testExecutionStatus.id` actually changed (`14539939`=Pass, `14539940`=Fail) before trusting it — if it didn't, treat that one execution as unconfirmed/blocked rather than guessing a result.
10. **For any execution that was already passing in step 6 (no fix made this run), find the responsible PR/commit** per the spec's "Finding the responsible PR/commit" section — don't just write "already fixed" in the comment. Locate the relevant file(s) the same way step 7 would have; `git log --oneline -n 30 -- <file(s)>` (and `origin/DEVELOPMENT` too if the local checkout is behind — same drift check as step 8) for a commit dated after the ticket's `created` field whose subject plausibly matches this scenario, `git show` it to confirm the diff actually explains the behavior, then build a PR URL from its trailing `(#<N>)` and the real `github.com/Eruditiontx/<repo>` (not any SSH host alias `git fetch` output shows). Carry the commit hash, PR link, author, and a plain paraphrase into step 11's Solution. If a real search turns up nothing plausible, fall back to noting it was already passing with the cause untraced — don't fabricate a citation. Skip this step entirely if step 6 found every execution still failing (nothing was "already fixed").
11. If a still-failing execution turns out to conflict with a **deliberate, documented design decision** elsewhere in the codebase (confirmed on `EI-3456`: rejecting an unknown-but-well-formed class code would revert `class_code_validator.py`'s documented anti-enumeration protection) — that's a confirmed, honest `Fail`, not a process blocker. It still goes through steps 9–13 exactly like any other result: `PUT` the real `Fail` (step 9), comment explaining *why* it's failing and what design tension it surfaces (step 12 below), transition to In Progress, and log `FAILED`. Don't divert this into "step 12's ... don't log" fallback — that's for genuine process failures only (unparseable ticket, untraceable code, an erroring API call, a write that won't confirm), not for a legitimate reason not to change the code.
12. Once every execution's real result is confirmed (whether all passed or not):
    - **Comment** on the ticket covering **Issue** (root cause), **Solution** (what was changed this run; or, for an execution already fixed per step 6, the PR/commit found in step 10 — link, hash, author, paraphrase, not just "already passing"; or, per step 11, that it conflicts with a deliberate design decision — cite what that decision is and where it's documented; or, for an ordinary unresolved failure, what was tried and what's still broken), and **Remarks** (edge cases, follow-ups, which executions if any still fail).
    - **Transition** the ticket to **In Progress**: call `getTransitionsForJiraIssue` and match by **target status name** (`to.name`, case-insensitive `"in progress"`), not by the transition's own `name` field — this board has a transition literally labeled "In Progress" (`id: "21"`) that actually targets `"TO DO (Exclude SKIPPED, INFRA)"`; the real one confirmed on `EI-3455` (2026-09-25) is `id: "3"` → status `"IN PROGRESS"`. Apply it, then `getJiraIssue` again and confirm `fields.status.name` is `"IN PROGRESS"` (case-insensitive); if not, flag it as unresolved in the summary but continue to the logging step regardless (the code fix and comment already happened and are worth recording).
13. Append one line per execution from step 9 to `BUG_FIX_LOGS`: `JIRA:<Bug ticket key>, EXEC:<Execution.Key>, TESTCASE:<Test Case.Key>, RESULT:PASSED|FAILED` — only after step 12 has run, not before. If step 6/7/8 never reached a confirmable result at all (code location couldn't be traced, a Zephyr write never took, etc. — not the deliberate-design-decision case from step 11, which does get logged), don't log anything for this ticket — report the blocker per the spec's "If something doesn't fit" instead.
14. **No confirmation needed before claiming/checking/commenting/transitioning/logging** — that part proceeds straight through once the real result is known. Committing/pushing the code change is the one exception: always ask the user first (see step 8), whether that happens mid-task (BackEnd, to reach a real verification) or after — and it may not be needed at all, if step 6 found it already fixed. Report what was done (ticket key, category, assignee before/after, already-fixed vs newly-fixed vs still-broken per execution, PR cited if any, file(s) changed if any, whether/what was committed, transition outcome) in the final summary.
15. Stop after this one ticket. Do not automatically continue to the next one — run `/zephyr-bug-fix-one` again for the next item.
