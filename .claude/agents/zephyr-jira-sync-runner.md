You run the full Zephyr/JIRA sync task defined in `.claude/tasks/zephyr-jira-sync.md`, using the same per-row logic as the `/zephyr-sync-one` command, but you keep going until every matching row is processed instead of stopping after one.

## Rules

- **Strictly sequential.** Process exactly one row at a time, fully, before starting the next. Never batch or parallelize JIRA/Zephyr calls across rows.
- **Source of truth**: `.claude/tasks/zephyr-jira-sync.md` for the env vars, column map, and decision logic. Re-read it at the start of the run.
- **Idempotent**: before processing a row, check `CSV_LOGS` for its column-B (`Execution.Key`) value — if it's already logged with *any* status (`PASSED`/`FAILED`/`SKIPPED`/`BLOCKED`/`NOT EXECUTED`), skip it. A `BLOCKED` row is not auto-retried — it stays logged until a human resolves it.
- **No confirmation needed.** Proceed straight through Zephyr comment/status updates without pausing to ask — print one line naming the row (columns B, F, G) and the action taken as you go, for visibility, but don't wait on a response before continuing. JIRA itself is never mutated (read-only JQL search/`getJiraIssue`).
- **Stop on ambiguity, not guess**: if a JQL search for column G returns more than one plausible match, append `<column B>, BLOCKED, REASON:<short description>` to `CSV_LOGS`, then stop and report the row instead of picking arbitrarily. Move on to nothing further until it's resolved.
- **Fail loud, don't skip silently**: if a row errors out (JIRA API error, Zephyr execution unclear, a `PUT` that doesn't actually change `testExecutionStatus.id` on re-`GET`, etc.), append `<column B>, BLOCKED, REASON:<short description>` to `CSV_LOGS`, then stop the whole run and report exactly which row and what failed — do not skip it silently and continue to the next row.

## Procedure (repeat per row until none remain)

1. Load the Excel workbook at `TEST_DATA_URL` (sheet `TEST_DATA_SHEET`) — it's a binary `.xlsx` file, so parse it with a Python/`openpyxl` script via Bash rather than `Read`ing it as text (see "Loading `TEST_DATA_URL`" in the spec). Filter to rows where column D (the assignee column, header exports blank but the values are real names) equals `Paul` (case-insensitive exact match).
2. Load `CSV_LOGS`; build the set of column-B values already logged, under any status.
3. Pick the first matching row (in CSV order) not yet in that set. If none remain, stop and report the final summary (see below).
4. Search JIRA (`JIRA_URL`'s project) via JQL for an issue whose summary matches column G. This task is read-only against JIRA (`searchJiraIssuesUsingJql`/`getJiraIssue` only) — no comment or transition is ever made on the JIRA issue itself.
   - **Match found** → record it on the **Zephyr execution** instead: `PUT https://prod-api.zephyr4jiracloud.com/v2/testexecutions/<column B>` with body `{"comment": "<p>JIRA <code>&lt;ticket key&gt;</code> Already Automated</p>"}` (e.g. `<p>JIRA <code>EI-3435</code> Already Automated</p>`) — **no `statusName`** in this call, since no test was run. Re-`GET` the execution and confirm the `comment` field actually changed before trusting the write (this comment-only shape is unconfirmed until exercised live — if the API 400s without `statusName`, or the comment doesn't show up on re-`GET`, fall through to the blocked case below rather than guessing a workaround). Then append `<column B>, SKIPPED, JIRA:<ticket key>` to `CSV_LOGS`.
   - **No match** → check whether `teacher-student-automation` already has an automated test covering this scenario (search by keywords from column G, not the Zephyr id). **Also check `CSV_LOGS` for an earlier row sharing this row's column F (Test Case.Key)** before writing anything new — the same test case can recur across multiple execution rows/cycles, so a test authored for an earlier row's column F may already cover this one; reuse/re-run it rather than duplicating. Only if genuinely no test exists (neither in-repo nor via a prior `CSV_LOGS` row), write one following that repo's conventions and run it for real against the live QA host (`https://eruditionsolutionsqa.com`). Then record the real Pass/Fail **and** a structured record in one call: `PUT https://prod-api.zephyr4jiracloud.com/v2/testexecutions/<column B>` with body `{"statusName": "Pass"|"Fail", "comment": "<STEPS/EXPECTED/ACTUAL as HTML>"}` — **no MCP tool works for Zephyr Essential** (confirmed against SmartBear's own docs: their MCP only supports Zephyr Standard/Advanced), so this is a direct REST call via Bash, using the token from `ZEPHYR_API_TOKEN` (in repo-root `.mcp.json`, generated via Jira profile → "Zephyr Essential API keys"). **The `comment` field is raw HTML, not markdown** (Zephyr's Swagger schema documents it as a plain string; its own comment editor renders `<p>`/`<b>`/`<ol>`/`<ul>`/`<li>`/`<code>` tags properly, but a plain string with `**bold**`/backticks/`\n` gets inserted as one flattened, literal text run — confirmed by testing). The `comment` must cover three sections in order — STEPS (what the test actually does, as `<p><b>STEPS</b></p>` + numbered `<ol><li>`), EXPECTED (what column G / the test's intent says should happen, as `<p><b>EXPECTED</b></p>` + bulleted `<ul><li>`), ACTUAL (what really happened on this run, as `<p><b>ACTUAL</b></p>` + bulleted `<ul><li>` with `<b>PASSED</b>`/`<b>FAILED</b>`) — write all three in plain, everyday language, as if explaining the test to a non-technical reader (a PM, a teacher, a ticket reviewer) rather than another engineer: no status codes, endpoint paths, pytest output, or file names in the comment text; use `<code>` only around a value the reader genuinely needs verbatim (e.g. the malformed input tried), not around internal identifiers. See "Recording the automation" in the spec for the exact template. Still no `::`, curly braces, or em dash anywhere in it — those have triggered a `400 "Invalid Payload"` from this API before. This is the only durable record mechanism available: Zephyr Essential has no comment endpoint for test cases and no attachment endpoint at all, only this execution-level `comment` field. The status field is `statusName` — `status`/`statusId`/`testExecutionStatus` all silently no-op with a `200`, so always re-`GET` the execution after the `PUT` and confirm `testExecutionStatus.id` actually changed (`14539939`=Pass, `14539940`=Fail, per `GET /statuses?projectKey=EI`). Then append `<column B>, PASSED, JIRA:NONE` or `<column B>, FAILED, JIRA:NONE` to `CSV_LOGS` (matching the confirmed Pass/Fail result). A `FAILED` result is a genuine bug find — log it and keep going, don't treat it as a run failure.
   - **Unresolvable** (ambiguous JQL match, a JIRA/Zephyr API error, or a Zephyr write that didn't actually take per above) → append `<column B>, BLOCKED, REASON:<short description>` to `CSV_LOGS`, then stop the whole run per the "Fail loud" rule above.
5. Go back to step 3 for the next row.

## End of run

Report a summary: total rows processed this run, broken down by status (`SKIPPED` closed-as-automated count, `PASSED`/`FAILED` breakdown from fresh Zephyr executions, and any `BLOCKED` row with its reason).
